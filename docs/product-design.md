# OrderPact 产品设计

用户通过自己的 Agent 发布链上需求，供应方使用自己的 Agent 发现订单、报价并履约。合约记录权威订单状态与货款，客户端和索引服务可以替换。当前已经验证同一电脑上独立进程的交易闭环与恢复，后续再验证跨框架、跨设备和跨索引的互操作。

## 产品定位

服务对象是希望直接表达需求、发现交易机会并自主选择交易方的普通用户及服务提供者。Agent 的首要价值是整理复杂需求、发现歧义、筛选公开订单和解释候选；用户保留交易决定权。用户不必学习合约字段、事件查询和签名协议。

Agent 指用户已有的 Codex、Claude 或 API 驱动的 Agent。它负责理解和履约，本项目交付 Skill、协议 SDK 和可执行工具，不再以自建交互客户端或本地模型作为接入前提。用户在原有对话中确认；工具和索引在宿主执行环境内按需运行，项目方退出后仍有直接读链和交易路径。

公开可检索性、排序自主和宿主可替换性是原则；上链不等同相同曝光或同等成交机会。宿主根据能力、预算、期限和用户偏好选单；本项目不提供不可替换的中央目录或付费自然排名。

通用协议描述交易关系与生命周期；复杂订单包含原始描述、目标、技能、必须项、交付物、排除范围、条件分支、语言与格式、预算、期限和待澄清问题。任何未回答的问题都会阻止发布。复杂条款由双方明确接受，链上不会自动执行所有语义。自动验收是可选能力，不作为第一优先级。

订单从发布时就写入合约。公开信息可以被任何索引服务读取，搜索入口不拥有订单。公开协议本身不构成永久收费权。

## 第一场景

先以公开资料调研和报告类任务验证“描述复杂需求—发现候选—用户直接成交”。例如：比较三个开源协议，中文 Markdown 交付，必须附官方来源，不猜测未知数据，不注册账号；来源不可访问时注明原因。用户人工检查并确认报告。这是一种试点任务，不将报告质量自动化作为前提。

当前 v0.4 提供 demand.complex.v1、p2p-orders Skill、一次性 JSON 工具、公开分页发现和用户授权后执行。宿主生成结构化 terms，工具校验而不再调用另一个模型。已验证工具进程闭环；示例的理解输入、授权与交付仍为测试夹具，不代表真实研究完成或跨产品测试。

早期 web.extract.product.v1 和 web.fetch.products.v1 采集模板已在公开版清理中移除；当前范围聚焦 demand.complex.v1。增加任务类型不应要求重写托管逻辑。

## MVP 用户流程

1. 用户用日常语言描述需求。Agent 生成复杂草稿，缺失项和歧义由用户补充，未澄清不允许发布。
2. 用户检查完整公开内容、期限和资金规则，明确确认后发布；草稿不自动上链或付款。
3. 供应方宿主读取完整分页需求，自己理解复杂条件并向用户解释候选；标签工具仅可选粗筛。用户选中后在原对话确认报价。
4. 买方挑选任意有效报价，确认供应方、金额及完整条款；合约验证签名、固定供应方并锁款，不自动选择最低报价。
5. 供应方确认已锁款后履约，用户确认提交公开交付说明或小数据；当前不会执行订单文字里的命令。
6. 买方查看实际交付后手动确认或提出异议；无异议期满仍可按原合约规则结算，关闭客户端不暂停倒计时。
7. 争议由约定评估方裁定；未交付或裁定超时按固定规则退款。开发评估方默认离线，不代表已提供仲裁服务。
8. 收款方确认提取自己的余额。每次动作绑定钱包、部署、完整条款及订单状态；预览后变化须重新确认。

## 开发优先级（v0.4，Skill 优先）

P0：Skill、可分发工具运行时、结构化协议、无钱包分页发现、交易提案和原对话授权执行。本轮已实现，不要求用户打开额外客户端或本地模型。

P1：让真实的独立宿主按 Skill 完成同一任务，验证需求原意、语义匹配解释、用户授权范围和故障恢复。宿主本身理解自然语言，项目侧不训练或强制部署模型；按需要增加候选检索索引和词表。

P2：发现完整性、垃圾订单处理、可替换索引、跨框架与跨设备互通；目标是索引服务失效时仍能重建，不设唯一目录和付费自然排名入口。全量本地匹配目前为线性扫描，需实测和进一步索引优化。

P3：公共测试网、生产签名与提醒、实际费用和争议机制审查；自动验收、更多抓取适配器及信誉系统按实际需求再排期。

## 范围

| 第一阶段 | 后续阶段 |
| --- | --- |
| 一条本地 EVM、一种测试支付资产 | 测试网及选择实际结算资产 |
| 发布起上链的公开订单 | 可选的隐私需求发布方式 |
| 每单一名买方，允许多供应方独立报价，选定一方 | 多方任务、阶段交付、复杂议价 |
| 复杂需求模板；可选快照及商品页模板 | 更多领域的表达与匹配方式 |
| SDK、本地增量索引及链上跨进程通信 | MCP、跨框架客户端及独立远程索引服务 |
| 约定评估方、全额放款或全额退款 | 部分赔付、评估方选择与更成熟的争议机制 |

第一阶段不发行网络代币、订单 NFT，不开发新链。生产网络需按目标链的确认规则处理重组，不能照搬本地即时确认。

## 差异假设与已有项目

以下是待验证的产品选择，不视为首创性结论。

| 参考项目 | 已有能力 | 本项目验证重点 |
| --- | --- | --- |
| Virtuals ACP | Agent 服务发现、任务、报价及托管交付 | 买方需求从发布起上链，以及不依赖单一客户端的订单操作 |
| Olas Mech | 链上或链下服务请求与 Agent 交付 | 可协商订单和明确的验收争议条款 |
| x402 Bazaar | 付费 HTTP／MCP 资源发现及调用 | 异步结果订单的履约、验收和退款 |
| ERC-8183 | 任务托管与评估结算规范 | 在其思想基础上研究需求发现与超时规则；当前不宣称符合该标准 |

参考：

- [Virtuals SDK](https://github.com/Virtual-Protocol/acp-node-v2/blob/main/migration.md)
- [Olas 请求文档](https://stack.olas.network/mech-client/)
- [x402 Bazaar 规范](https://github.com/x402-foundation/x402/blob/main/specs/extensions/bazaar.md)
- [ERC-8183](https://ercs.ethereum.org/ERCS/erc-8183)

真正的差异证据是：用户无需理解链上技术也能表达复杂需求并确认交易；小供应方的符合条件订单可被检索；参与者能替换客户端和发现入口继续操作。当前验证相同实现的跨进程交易和分页覆盖，尚未证明真实模型理解质量、商业需求、百万订单容量或独立团队互操作。

## 收入设计

早期优先访谈买方是否愿意为预算、采购和对账工具付订阅费，供应方是否愿意为接入、托管和获客付费。也可以自营一个数据服务验证需求，但应披露自营身份和排序原则。

稳定交易出现后，再评估成交费、托管基础设施、索引 API 或验收服务收费。协议收费应在成交前明确，已有订单的费率和规则不被管理方事后修改。当前原型费率为零。

成交额不等于收入；托管货款不属于运营收入。评估利润时计入模型、抓取、RPC、链上费用、退款、人工争议和获客成本。

## 试点目标

以下为计划目标，而非已有业务数据：5 个独立买家、3 个独立供应方、50 笔真实需求订单。至少使用两种独立客户端和两个可替换索引入口。先在测试网验证流程，再决定是否进入受限小额真实支付。

| 要验证的问题 | 指标 |
| --- | --- |
| 用户能否表达复杂需求 | 原意保留、未澄清项、草稿修改次数、用户理解程度 |
| 公开发现是否有用 | 检索覆盖、筛选原因、符合条件的新参与者能否被找到 |
| 买家是否愿意直接交易 | 付费意愿、再次下单、对现有方案的替代原因 |
| 供应是否有效 | 有效报价数、报价时间、成交率 |
| 自动化是否有价值 | 单笔人工介入次数、完成时间 |
| 交付是否可靠 | 按时通过验收率、异议率、争议处理时间 |
| 开放接口是否有效 | 跨客户端、跨索引完成交易的比例 |
| 经济性是否成立 | 单笔贡献毛利、总成本、退款与客服成本 |

停止或调整条件包括：订单主要来自补贴与测试；买家无复购；验收人工长期高于订单毛利；单一固定 API 明显更便宜可靠；供应方不愿承担默认争议风险。
